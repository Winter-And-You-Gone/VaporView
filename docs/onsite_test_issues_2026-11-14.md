## 002：AI-8 模块 `0x66` 新错误 `0x40`

### 现场证据

- 13:10:02.085，sequence 12：AI-8 连接成功，已收到设备有效数据。
- 13:10:05.024，sequence 24：启动等待 3 秒后仍异常；模块 `0x00000066`，新增及累计错误均为 `0x00000040`。
- 该管理事件的 source 为 `0x46`，模块页为 `0x66`（寄存器基址 `0x6600`），事件状态字为 `0x00000C83`。其中 AI-8 专用 STATUS.bit1 为 online，bit7 为汇总错误；它可以通信在线且同时报错。

### 已确认原因与边界

`0x40` 是 bit6，定义为 `ERR_DEVICE_REPORTED_ERROR`。AI-8 RTL 在采集结果的 `core_alarm != 0` 或 `core_host[9:8] != 0` 时锁存该位；设温读回不匹配或 Modbus exception 等命令结果也可以置位。它不是“只有一个通道”的错误，也不能直接解释为 USB 或串口断开。

本次单条事件没有携带 AI-8 的完整 alarm/control/host 字，不能进一步断言是探头断线、输入超量程或哪种仪表报警。粘滞错误记录曾发生的错误，不单独证明当前仍在报同一种故障；启动提示表示宽限期结束时未通过完整健康判断。

### 说明书核对与现场补充（2026-11-14）

- 第 23 页（22/47），5.1 通道参数：`In01..In96` 的个位 1..4 选择输入规格组，个位为 0 关闭该路测量。未用通道可按实际配置关闭；不能把 `In` 与选择传感器类型的输入组参数 `InP` 混为一谈。

约 13:31～13:32，通过正在运行的 GUI 的 FPGA → 传感器页只读观察，确认：

| 项目 | 现场读值 | 判断 |

| 所选通道 | `0x661C=1`（CH1） | 当前仍采集 CH1，本次未改变通道 |

## 004：TFA 连接失败提示延迟约 202 秒

- 关联问题：003。启用至失败的日志间隔为 `202.400 s`，不是界面中启动健康检查使用的 3 秒。
- 已确认代码原因：`FpgaDeviceController::confirmConnection` 为不同设备选择轮询间隔地址，但未覆盖 TFA（source `0x45`）。它将 `pollAddress` 回落为 `0`，仍计算 `max(8000, 3 * registers_[pollAddress] + 5000)`。
- `readAll()` 会读取地址 `0x0000`；当前下位机 `system_registers.v` 在该地址返回系统 ID `0x00010101`（65793），不是毫秒间隔。因此理论等待为 `3 * 65793 + 5000 = 202379 ms`，与本次实测 `202400 ms` 一致。
- 影响：延迟连接失败提示；不能解释或修复 TFA 串口本身没有有效数据的问题。其他没有映射到轮询间隔地址的设备也应在修复时检查同一路径。
- 修复方向：对没有毫秒轮询间隔的设备使用明确的默认期限；只有合法的轮询间隔地址参与计算。TFA 的 `0x653C` 单位为 FPGA tick，不能未经换算当毫秒使用。
- 状态：保留独立软件问题记录，按用户本轮忽略 TFA 的要求不继续处理。若后续修复，应覆盖“无有效数据按正确期限失败”和“期限内收到数据成功”的定向回归，并在 `build/Release` 验证后交付。

## 007：环境趋势图纵轴未围绕当前可见数据居中

### 用户现象与预期

- 用户提供的本轮“环境与测距”截图中，气压曲线靠近下沿，湿度曲线几乎压在底边、图内大部分区域空白；温度只在约 22.5°C 附近轻微变化。截图横轴为 13:28:07～13:28:18，约 11 秒；温度纵轴刻度约 22.43～22.50°C、湿度约 72.19～72.37%RH。
- 用户要求：图内所有可见有效点应尽量在纵向居中的区域显示，与上下边界保持余量；数值稳定或只有微小变化时，曲线应在纵轴中部，而不是长期挤在底部或顶部。
- 本次按用户要求查原因并记录，没有修改绘图实现、测量数据或正在运行的应用状态。原始截图只保留本地，不提交图片。

### 已确认的绘图原因

气压、HC2A 温度、HC2A 湿度分别创建同一个 `EnvironmentTrendSparklineWidget`，实现位于本地 `c76b4d5b` 的 `src/ground/widgets/TelemetryPanels.cpp`。三图共用以下范围计算，所以该问题不是某一个传感器专属的显示路径。

1. **横纵轴使用的数据范围不一致。** `appendSample()` 最多保留 160 点（常量第 27 行，追加/移除逻辑第 236～270 行）；`collectFiniteSamples()` 收集整个缓存，没有按可见时间窗筛选。`makeAxisState()` 第 639～642 行直接对这些点计算最小/最大值。之后 `makeXAxisState()` 第 579～607 行才根据控件宽度和每格约 1 秒确定最近一段横轴窗口；较旧点在 `paintEvent()` 绘制时被裁掉，却仍参与纵轴范围。以截图约 11 秒窗口、约 0.9～1Hz 数据为例，160 点覆盖的历史明显长于当前可见范围；旧高值仍可将当前低位稳定数据压向底部，旧低值同理可将曲线推向顶部。窗口缩放也会改变可见时间长度，但当前纵轴不会相应改为只统计新窗口。
2. **非恒定数据没有上下余量，也没有合理的最小显示跨度。** `makeAxisState()` 只有在 `max-min < 1e-6` 时才额外保留上下各 1.0 单位；只要出现 0.01 这样的微小差异，就直接把缓存极值当纵轴上下边界。第 430～433 行使用 `(value-min)/span` 映射坐标，最小点必然落在底边、最大点必然落在顶边。并非只有测量完全相同时才需要居中和留白。
3. **边界裁剪会加重贴边观感。** 第 437 行将曲线裁剪到 `plotRect`，线宽为 1.8、末点圆点半径为 2.4；极值与边界重合时，线或圆点会被截去一部分。最新点横坐标也直接锚定右边界；修复纵轴时需一并保留点标记所需的绘制安全余量。

这里的“历史极值”是代码已确认的通用触发机制。截图没有附完整 160 点及当时轴范围快照，本次没有在应用里导出原始样本，因此不声称已还原截图中具体哪一个旧样本控制了轴上限/下限，也不由此断言测量数据本身异常。

### 数值诊断与现有覆盖缺口

使用与现有代码相同的映射公式做了以下数值核对，属于说明机制的人工构造示例，不是本次传感器原始数据：

- 若缓存包含已移出窗口的 72.37，缓存最小值为 72.19，而当前可见点为 72.19～72.20，则可见曲线仅占从底部算起的 `0%～5.56%`，即使图内已经看不到那个 72.37 的旧点。
- 即使没有旧极值，若全部数据仅为 22.48～22.50°C，当前算法仍会把这 0.02°C 的小变化铺满整个高度：22.48 在底边、22.49 在中部、22.50 在顶边。顶部读数仅显示 1 位小数，还会使“数字几乎不变、曲线却占满高度”的观感更明显。
- `tests/device_panel_coordinator_test.cpp` 已检查单样本时上下各 1 的刻度，以及时间轴标签、窗口宽度和时间跨度；没有覆盖“旧极值移出横轴后不再影响纵轴”“小幅非恒定变化仍有上下余量”“可见数据中点靠近纵轴中心”。因此现有这些断言不能证明用户要求的居中显示已经满足。本次未运行 GUI 测试，也未新增回归实现。
