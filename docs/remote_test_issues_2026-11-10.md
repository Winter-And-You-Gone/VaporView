# 远程工控机测试问题记录（2026-11-10）

本文记录本轮远程测试遇到的问题、排查结论和建议处理方式。建议方案尚未实现，修复后需补充验证结果。

## 001：SkyCore 控制台重复输出无具体内容的诊断提示

- 状态：已记录，待修复。
- 测试程序：远程工控机上的 `VaporViewSkyCore.exe`。
- 现场现象：控制台持续重复输出“设备采集器输出了原始诊断信息。”，无法从文字判断涉及哪个设备、实际发生了什么。
- 截图可确认：运行配置为 `debug`，本机 IPC `127.0.0.1:39001` 和 TCP 遥测 `0.0.0.0:39100` 已开始监听。监听成功不等于设备采集正常。

### 已确认原因

当前源码 `src/sky/devices/SkyDeviceManager.cpp` 的 `connectSerialCollector()` 为采集器设置了原始日志回调。每次回调都会发布一条 `Info` 级别、事件名为 `device_collector_output` 的日志，消息正文固定为上述提示。

真实诊断内容保存在结构化字段 `process_output` 中，设备标识保存在 `device_id` 中。因此，不同的原始消息在控制台上表现为同一句提示，频繁回调时形成刷屏。

仅凭截图不能确定具体设备和原始消息，也不能判断是正常采集输出还是反复连接失败。远端程序版本是否与当前源码一致尚未核对。

### 建议解决方法

1. 控制台摘要包含设备名称和有意义的原始诊断摘要，让现场人员能直接识别设备及事件；原始完整内容继续保留在本地结构化日志中。
2. 对同一设备的重复消息合并或限频，周期输出重复次数；新错误和状态变化及时显示，避免被普通采集信息淹没。
3. 逐步将高频采集明细归为调试日志，连接、断开、异常等事件采用对应级别的结构化日志；不要把所有原始回调一律视为普通信息或错误。

### 现场排查与修复验收

- 先在工控机本地结构化日志中检索 `device_collector_output`，查看 `device_id` 和 `process_output`，确定实际刷屏来源后再实施针对性修复。
- 验收时覆盖正常采集和设备连接失败两种情况：控制台应能识别设备和原因，重复输出受控，新错误及时可见，完整原始诊断仍可在本地日志中追查。
- 本文只记录现象与建议，尚未修改程序，也未完成远端实机修复验证。

原始日志、截图、崩溃 dump、导出包及包含凭据的测试样例仅在本地保留，不纳入 Git 提交。

## 002：本机 ping 工控机超时，反向 ping 成功

- 状态：已记录，待现场排查，尚未确认根因。
- 用户报告：工控机 `192.168.1.4` 可以 ping 本机 `192.168.1.2`，本机 ping 工控机超时；本机 H300 的 AP 灯亮，工控机 H300 的 AP 灯灭。
- 说明书依据：本地《H300模块使用说明书1.5》第 6 页说明 AP 灯在 AP 模式下亮、STA 模式下灭；第 7 页说明网络只应有一个 AP，其余为 STA。因此两端 AP 灯一亮一灭符合角色配置，不能据此认定工控机数传故障。
- 初步判断：优先检查工控机 Windows 防火墙的入站 ICMP Echo Request 规则和当前网络配置文件。反向 ping 成功包含请求与响应两个方向；若确认走的是 H300 链路，说明该链路已有双向报文通过。此判断不排除多网卡路由、地址冲突或其他过滤问题。

### 建议排查顺序

1. 保持 SkyCore 运行，在本机 PowerShell 执行 `Test-NetConnection 192.168.1.4 -Port 39100`，先确认实际业务 TCP 端口是否可达，记录 `TcpTestSucceeded`。ping 超时不能单独判定 SkyCore 无法连接。
2. 若 TCP 成功，使用 VaporView 的 Remote/TCP 连接 `192.168.1.4:39100`，继续验证应用通信。
3. 若 TCP 失败，在工控机确认 SkyCore 仍监听 `0.0.0.0:39100`，检查防火墙是否允许来自 `192.168.1.2` 的入站 TCP 39100；需要 ping 验证时，单独允许该来源的 ICMPv4 Echo Request。优先使用限定来源的规则，不整体关闭防火墙。
4. 若仍失败，核对两端网卡 IP、掩码、路由及 H300 的 RSSI 指示，确认没有同网段多网卡抢路由或重复 IP，再判断无线链路问题。

上述命令和配置检查尚未在远端执行，等待现场结果。

### 后续结果

用户已在本机执行端口检查：源地址 `192.168.1.2`、接口“以太网”、目标 `192.168.1.4:39100`，`TcpTestSucceeded : True`。因此该次 TCP 探测成功；ping 不通的原因仍未确定，不应继续将其作为业务连接失败的依据。

## 003：端口探测成功，但 VaporView 因代理错误无法连接

- 状态：已定位底层错误，待修复和复测。
- 现象：端口探测成功，GUI 配置也是 `192.168.1.4:39100`，但点击连接立即提示“地面端遥测链路异常”和“无法打开天空端 TCP 数传链路”。
- 本机日志证据：2026-11-10 21:28:50 和 21:34:23（UTC+8），当前 VaporView 进程的 `ground_telemetry_link_error` 事件均记录 `system_error = The proxy type is invalid for this operation`。时间与截图一致。这里只摘录必要错误文本，不提交原始日志。
- 源码检查：`TcpTelemetryLink::connectToHost()` 和 `connectToHostAsync()` 创建的 `QTcpSocket` 未显式禁用代理。当前错误指向 socket 使用的代理类型不适用于本次操作；具体代理配置来源尚未确认。
- 提示问题：`GroundTelemetryService` 将实际原因存入 `system_error`，但界面只显示通用警告；主窗口随后提示检查 SkyCore 监听，未呈现代理错误，容易误导排查。

### 建议解决方法

1. 对要求直接连接的设备遥测 TCP socket 显式设置 `QNetworkProxy::NoProxy`，覆盖同步和异步入口；限定到设备链路，不全局关闭更新等互联网请求的代理。
2. 连接失败时在界面显示实际 socket 错误和目标地址，避免所有失败都只建议检查 SkyCore 是否启动。
3. 临时现场验证可在用户方便时关闭系统代理并重启 VaporView 后重连；这只是验证路径，尚未执行，也未证明具体代理来源。
4. 修复验收应包含启用代理环境下的本机模拟连接与 H300 实机连接，确认正常收到天空端状态，并验证真实失败原因可见。当前尚未修改代码或进行此项验收。

## 004：远程 FPGA 连接无数据，界面只提示收到命令结果

- 状态：确认命令失败，远端具体失败原因待查。
- 现场截图：天空端握手成功，基础遥测 10 Hz、状态 1 Hz，但设备无数据；21:40:52 的命令响应及设备操作结果均为警告。
- 本机日志：对应命令 `command_id=60` 的 `ack_error_code` 和 `result_error_code` 均为 `10`，源码定义为 `ConfigApplyFailed`（配置应用失败）。因此“已收到结果”不代表执行成功；现有日志未在这两条记录中呈现具体失败原因。
- 用户称已选择 FPGA 模拟器；截图只能确认远程及 FPGA 路径，无法确认工控机进程已启用模拟后端。远程设备由工控机进程持有，本地模拟器选择不会自动将普通远程 SkyCore 变为模拟服务。

### 建议处理与验证

1. 在工控机退出原 SkyCore 后，从程序目录运行 `./VaporViewSkyCore.exe --fpga-simulate-data --telemetry-transport tcp --telemetry-host 0.0.0.0 --telemetry-tcp-port 39100`。也可使用独立 `VaporViewFpgaSimulator.exe` 并显式指定相同监听地址和端口；二者选其一，避免端口冲突。
2. 本机重连 `192.168.1.4:39100`，同步配置后在 FPGA 页确认模拟标识和连接状态，再按需启用传感器及 ADC/DLIA 采集。基础遥测频率不代表传感器已有数据，板卡连接也不等于各模块启动。
3. 若仍失败，检查远端对应操作的实际错误及 FPGA 状态详情，不根据通用命令响应推断成功。当前不能仅凭错误码断言缺驱动或找不到实体板卡。
4. 软件改进：命令结果摘要显示成功/失败、操作名称、错误码及可用的具体原因；远程模式明确模拟服务必须在天空端启动。

上述启动建议已核对 `src/app/sky_core_main.cpp` 和 `docs/fpga_simulator.md`，尚未在工控机执行验证。

## 005：标题栏连接按钮在远程模式下仅连接数传

- 状态：已确认当前代码行为，待调整。
- 用户预期：点击标题栏连接后自动连接设备，而不是只打开 TCP 链路。
- 代码事实：`GroundMainWindowConnection.cpp` 的 `onConnectClicked()` 在本地 FPGA 路径建立逐设备连接队列；远程 TCP 路径调用 `openTcpAsync()` 后直接返回。链路打开回调请求状态，收到状态后标记握手成功，没有接续批量连接设备；Ground 当前没有发送 `ConnectAllDevices` 的调用。
- 因此当前同一按钮在本地 FPGA 和远程模式下语义不一致。遥测已连通、握手成功不意味着设备已连接或采集已启动。此行为与问题 004 的单次设备操作失败应分开处理。
- 建议：标题栏统一为连接当前配置中启用的设备；远程先完成链路、握手和配置同步，再按当前直连/FPGA 路径执行设备连接。分别呈现链路状态及设备成功、失败、未启用状态，失败显示具体原因。记录、激光输出和 DAC 等独立动作保持各自控制，不附带自动开启。
- 验收：远程直连与远程 FPGA 均验证一次点击完成预定设备连接；重复点击和链路重连不重复下发启动操作；部分设备失败时能看到具体结果。尚未修改程序。

## 006：远程 FPGA 模拟数据摘要与详情不一致，部分模块无数据

- 状态：已记录，需分别验证数据来源、状态与新鲜度。
- 截图显示 EPSILON、PTB、TFA1500、AI8 有数据；HMP、波形、RD105、BMP390、SHT45 摘要为无数据。与此同时 RD105 温度曲线、内部气压及温湿度已有数值；运动控制未连接。
- HMP：当前 `remoteDeviceDataValid()` 在 FPGA 路径直接将 HMP 判为无效；内部 SHT45 温湿度不等于外部 HMP 数据。应明确显示该路径不提供 HMP，避免与绿色连接状态产生歧义。
- RD105/BMP390/SHT45：模拟器支持相应数据，截图已有详情值，不能概括为未实现模拟。摘要依赖远端设备状态及最近数据时间，需核对与详情使用的数据路径是否一致，也需排除详情残留旧值。尚未确认具体根因。
- 波形：截图各波形频率为 0，需分别确认 ADC/DLIA 已启动及远程波形上传已启用。连接代码会先发送 `DisableWaveformStreaming`，不能由设备按钮绿色推断已有波形；进一步检查启用请求及数据接收。
- 运动控制：按 `docs/emfwc3.md`，EM-FWC3 是独立本地 SDK/串口控制链路，不通过 FPGA 或 SkyCore 转发，因此启动远程 FPGA 模拟器不会自动提供运动控制数据。需要独立模拟接入才能覆盖此项测试。
- 建议：摘要和详情统一有效性、新鲜度及来源判断；区分不支持、未启用、未连接、等待数据和过期，不全部归为无数据。补充远程模拟场景验收，核对摘要、曲线、频率一致性；运动模拟作为独立需求评估。
- 本条仅记录与分析，尚未修改程序或进行实机验证。

## 007：远程运行时界面严重卡顿，按钮悬停反馈延迟

- 状态：已取得现场主线程栈证据，尚未完成具体控件及外部触发源定位。
- 现场进程：本机 Release VaporView，PID 44828，GUI 线程 52964。多次检查在 Responding=False/True 之间变化，日志仍间歇更新，不能认定进程已崩溃或永久死锁。
- 前期约 3 秒 CPU 采样中 GUI 线程累计消耗约 2.28 秒 CPU；这只代表该采样区间的负载，不代表全部卡顿时间都在计算。
- 后续第一轮 25 次 GUI 线程栈采样全部落在文本更新触发的 UI Automation 等待链；第二轮再次捕获相同等待链，也看到绘制栈。两轮不是连续 CPU profiler，不能把样本比例当作整段运行的耗时占比。
- 共同调用链为 `QWidgetLineControl::internalSetText` → `QAccessible::updateAccessibility` → Windows `UiaRaiseAutomationEvent` → 系统等待函数。部分栈包含 `QComboBox::setCurrentText` 或 `setCurrentIndex`。无私有符号的 Windows/Qt 导出符号只能作为路径线索，不据邻近符号名称判断内部实现。
- 结论：采样时 GUI 主线程被辅助功能通知路径阻塞，可解释鼠标悬停及输入响应延迟。尚不能确定是哪一个 UI Automation 客户端、具体控件或刷新源导致；不应归咎于 H300，也不能据此全局禁用辅助功能。
- 限制：当前未找到可用的应用 PDB，应用栈帧仍为地址，尚未精确映射到源码；未进行关闭外部客户端或调整刷新行为的对照实验。
- Windows 在 22:08:26（UTC+8）记录过 `RADAR_PRE_LEAK_64`，仅作为独立线索，不证明泄漏或它与卡顿的因果关系。

## 008：Release 未生成 PDB，影响卡顿定位

- 检查结果：`CMakePresets.json` 的 Windows preset 使用 `Release`；当前 `build/Release/CMakeCache.txt` 中 C++ Release 参数为 `/O2 /Ob2 /DNDEBUG`，实际构建规则没有 `/Zi` 或 `/Z7`，链接参数没有 `/DEBUG`；`cmake/CompilerOptions.cmake` 未补充符号生成配置。
