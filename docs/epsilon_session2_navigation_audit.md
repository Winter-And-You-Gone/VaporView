## ECEF 核验

### 协议与方法

官网和本地手册第 11.2.17 节均规定：`MSG_ECEF_POS` 的 ID 为 `0x5D`，负载长 24 字节；X、Y、Z 位于负载偏移 0、8、16，均为 `float64`，单位米。

核验脚本按本次记录的 VVRAWDAT 文件头及 36 字节记录头逐条取出 FDILink 帧，检查长度、起止字节、帧头 CRC8 和负载 CRC16，再从帧偏移 7 开始按三个小端 double 解码。CRC16 使用初值 0 的 CCITT 计算，与帧内校验值比较。

### 实测结果

- 共 57,913 个 `0x5D` 帧，帧结构与 CRC 检查全部通过。
- 首个原始帧解码：

  | 分量 | 原始报文值（m） |
  | --- | ---: |
  | X | 365504288.84676194 |
  | Y | 13374884.312994305 |
  | Z | 58148.007466678944 |

- CSV 中 ECEF 地心距离范围为约 365,748,809.49～365,748,964.45 m，中位数约 365,748,866.98 m，远超地表附近应有的约 637 万米。
- CSV 首条经纬高为纬度 `30.130669989°`、经度 `120.074031181°`、高度 `8.145019 m`。将该高度暂按 WGS84 椭球高计算，得到：

  | 分量 | 经纬高换算值（m） |
  | --- | ---: |
  | X | -2766678.9799219687 |
  | Y | 4777761.31381025 |
  | Z | 3182914.1326541607 |

  对应地心距离约 `6372790.45 m`。此处仅用于数量级和位置一致性检查，不代表已确认设备高度基准；海拔与椭球高的差异无法解释数亿米的异常。

### 可以和不可以得出的结论

异常存在于保存的原始设备报文中，且校验完整，因此可以排除本次 3D 渲染或 CSV 格式化生成这些数值；普通随机串口传输损坏也不符合全量 CRC 通过的现象。

应重点核查设备固件的 ECEF 输出实现以及固件与公开协议版本是否匹配。**尚不能凭离线记录确定具体固件缺陷，也不能断言硬件损坏或出厂标定失败。** CRC 通过只证明报文完整性，不保证数值在物理意义上正确。

## 航向核验

### 数据结果

- 按标准归一化四元数公式提取 yaw，与 CSV 的 `yaw_deg` 比较并将差值环绕到 ±180°：绝对差中位数约 `0.00000642°`，99 分位约 `0.00002537°`，最大约 `0.00003479°`。
- 因此，该记录的四元数与欧拉航向高度一致，没有证据支持两种姿态表示之间存在几十度差异。
- 使用 `atan2(vel_e_mps, vel_n_mps)` 计算运动方向，筛选水平速度大于 `0.2 m/s` 的 53,305 条记录：与 `yaw_deg` 的绝对差中位数约 `42.70°`，90 分位约 `77.46°`，环绕后的有符号差算术平均约 `41.01°`。最后一项不是圆周统计均值。
- 全记录最大水平速度约 `3.69 m/s`。低速、侧向运动、倒退或模组与载体方向不一致都可能使航迹方向不同于机体航向。

这些差值**不是设备真实航向精度的测量结果**：本次没有独立真北/载体朝向参考，也没有筛选已确认直线前进、安装关系固定的标定区间。不得将 `42.7°` 直接作为箭头或设备的固定补偿角。

### 状态信号与限制

- CSV 的 `heading_valid`：57,337 条 false，574 条 true。
- CSV 的双天线航向量测更新位（`update_status_bits` bit 5）：47,438 条置位。
- 常见滤波状态值为 927（55,746 条）、879（2,162 条）、287（3 条）。

`heading_valid` 属于原始 GNSS 状态，不能等同于融合姿态的整体有效性；这些字段也可能来自不同报文时刻。上述现象需要结合原始报文时序及固件定义核查，不能据此认定整个记录没有可用航向。

### 手册对安装与出厂标定的要求

本地手册第 5.5、5.6 节定义模组 X 轴为前向，Z 轴向下，X 轴指向真北时偏航为零。第 8.1、8.2.1、8.3 节要求按实际安装配置模组与载体的对准偏移、双天线航向偏移和天线杆臂；调平不消除航向安装偏差。第 10.10.5 节说明惯导及双天线安装误差角校准与安装条件有关。

出厂校准针对传感器本身，无法预先知道用户的安装方向、天线位置及载体前向。因此设备已出厂调试与使用时仍需安装配置并不矛盾。但本次未取得实际安装参数，不能认定安装错误就是航向差的原因。

手册第 8.1 节与第 8.3 节关于主辅天线前后布置的文字存在不一致；不应只凭其中一句设置方向。应结合轴向图、`#fante` 定义及适用固件向厂商确认。

## 系统故障状态

独立解码原始 `0x50` 系统状态帧，共 289,565 帧，`System_status` 全部为 17，即 `0x0011`。

按官网和本地手册状态表，bit 0 为系统故障，bit 4 为气压计故障。这是设备记录中的真实状态位，应向厂商确认其在该型号、固件中的含义。尚无证据建立这些状态位与 ECEF 异常之间的因果关系。

## 对前述口头判断的更正与当前代码行为

1. “当前 ECEF 阈值没有挡住记录 2”是不正确的。基线代码 `include/geo/GeoTypes.h` 的 `isPlausibleEcef()` 接受范围为地心距离 5,000,000～8,000,000 m；上述异常值会被拒绝。
2. `src/geo/CoordinateTransform.cpp` 的 `resolveEcefFromLlh()` 在 ECEF 无效且具有可用 WGS84 椭球经纬高时重新计算 ECEF；`src/geo/SessionTrackReader.cpp` 会调用该流程。当前 reader 对未声明高度基准的记录默认赋予 WGS84 椭球高，这属于程序假设，不是本次核验确认的设备事实。
3. `tests/map3d_real_data_load_test.cpp` 已有相似异常 ECEF 的回归用例，验证拒绝异常坐标并回退到经纬高。此处是代码审阅结果，本轮未重新运行测试或 GUI。
4. `src/map3d/Aircraft3DLayer.cpp` 已显式将机体前向、NED、ENU 和 ECEF 基底转换；模型本身以 +Y 为前向不代表必然存在 90° 偏差。本轮没有独立 GUI 证据证明所有姿态渲染均正确，也没有证据要求增加固定轴向修正。
5. `src/map3d/AircraftHeading.cpp` 优先四元数、再回退欧拉航向；记录 2 的两者一致，因此切换数据源不能解释或解决这里统计出的几十度航向/航迹差。
